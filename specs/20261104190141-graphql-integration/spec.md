# Spec: GraphQL integration

## Goal
Add a GraphQL API to the server using only the npm `graphql` package. Schemas live in `.graphql` files and resolvers in JavaScript files, one pair per entity. This spec adds the first entity, **User**, with a `registerUser` mutation that inserts into the `user` table.

## Structure
```
server/
├── index.js                          # mounts POST /graphql
└── src/
    ├── controllers/
    │   └── UserCtrl.js               # UserCtrl class: static register() (database work)
    └── graphql/
        ├── index.js                  # loads schema files + resolvers, builds the schema, runs queries
        ├── schema/
        │   └── User.graphql          # User type, input and registerUser mutation
        └── resolver/
            └── UserRes.js            # UserRes: registerUser resolver
```

Future entities follow the same pattern: `schema/Auth.graphql` + `resolver/AuthRes.js`, `schema/Company.graphql` + `resolver/CompanyRes.js`. Nothing else needs to change to add them.

## Schema loading (`server/src/graphql/index.js`)
- Reads every `*.graphql` file in `schema/`, sorted by name, and joins them after a small base document:

```graphql
type Query { _empty: Boolean }
type Mutation { _empty: Boolean }
```

- Each schema file adds its operations with `extend type Query` / `extend type Mutation`, so files never clash. (GraphQL requires every type to have at least one field, hence the `_empty` placeholder.)
- Builds the schema once at startup with `buildSchema` from `graphql`.
- Imports every `*Res.js` file in `resolver/` and merges their default exports into one root object (`{ registerUser, ... }`). Two resolvers with the same name → startup error naming both files.
- Exports `executeGraphql({ query, variables, operationName, context })`, which calls `graphql()` from `graphql` with the schema, the merged root and the context.

## Endpoint (`server/index.js`)
- `POST /graphql` with a JSON body `{ "query", "variables", "operationName" }` (`express.json()` on this route only).
- Responds with the standard GraphQL result `{ data, errors }` and HTTP 200, or 400 when `query` is missing.
- Context passed to resolvers: `{ req }` (used later for auth).
- No GraphiQL page in this spec.
- The Vite dev server forwards `/graphql` to the server (`app/vite.config.js`, next to `/api`), so the React app can call it in development.

## User schema (`server/src/graphql/schema/User.graphql`)
```graphql
enum UserStatus {
  ACTIVE
  INACTIVE
}

type User {
  uuid: ID!
  firstName: String!
  lastName: String!
  email: String!
  status: UserStatus!
}

input RegisterUserInput {
  "Generated by the client (crypto.randomUUID())."
  uuid: ID!
  firstName: String!
  lastName: String!
  email: String!
}

extend type Mutation {
  registerUser(input: RegisterUserInput!): User!
}
```

- The internal `id` is not exposed; `uuid` is the public identifier.
- The `uuid` is **generated on the front-end** and sent in `RegisterUserInput`. The table's `DEFAULT (UUID())` stays as a fallback for rows inserted outside the API.
- Fields are camelCase in GraphQL and snake_case in MySQL; the controller maps them.

## Resolver (`server/src/graphql/resolver/UserRes.js`)
- Default export: an object of root resolvers, `{ registerUser }`.
- `registerUser({ input }, context)` calls `UserCtrl.register(input)` and returns the created user.

## Controller (`server/src/controllers/UserCtrl.js`)
- `UserCtrl` class with `static async register({ uuid, firstName, lastName, email })`:
  1. Trims all values and lowercases the email and the UUID.
  2. Validates: `uuid` must be a canonical UUID (`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`, hex); names and email required; email format; first/last name ≤ 100 characters; email ≤ 255.
  3. Inserts into `user` (`uuid`, `first_name`, `last_name`, `email`); `status` uses its table default.
  4. Reads the row back by `id` and returns `{ uuid, firstName, lastName, email, status }`.
- Errors returned to the client (as GraphQL errors, with `extensions.code`):
  - invalid input → `BAD_USER_INPUT`, message naming the field;
  - duplicate email (`ER_DUP_ENTRY` on key `email`) → `EMAIL_TAKEN`, "Email is already registered.";
  - duplicate UUID (`ER_DUP_ENTRY` on key `uuid`) → `UUID_TAKEN`, "This UUID is already in use.";
  - any other database error → logged on the server; the client gets `INTERNAL_SERVER_ERROR`, "Could not register the user." (no SQL details leaked).

## Register screen connection (app)
- `app/src/controllers/GraphqlCtrl.js`: `GraphqlCtrl.request(query, variables)` POSTs to `/graphql` with `fetch` and returns `data`. On failure it throws a `GraphqlError` (named export) with `message`, `code` and `field` from the first error's `extensions`, or `code: 'NETWORK_ERROR'` when the server can't be reached.
- `app/src/controllers/UserCtrl.js`: `UserCtrl.register({ firstName, lastName, email })` generates the user's UUID with the browser's built-in `crypto.randomUUID()`, sends the `registerUser` mutation and returns the user. A new UUID is generated on every submit.
- `crypto.randomUUID()` only exists in secure contexts: `https://` or `localhost`. Serving the app over plain `http://` on another host would break registration.
- `app/src/pages/Register.jsx`:
  - after client validation passes, calls `UserCtrl.register()` with trimmed values;
  - while waiting: the button shows a spinner and "Creating account…", fields are disabled, double submits are ignored;
  - success: the card switches to **Account created** with a success alert ("Welcome, <first name>!", "Your account for <email> has been created.") and a **Go to sign in** link;
  - server error with a `field` (e.g. `EMAIL_TAKEN` → email, `BAD_USER_INPUT` → that field): shown under that field;
  - any other error (network, `INTERNAL_SERVER_ERROR`): a danger alert above the button. Editing any field clears it.

## Dependencies (allowed)
- server: `graphql`.
- app: none new (uses `fetch`).
- No other new dependencies.

## Acceptance criteria
1. `POST /graphql` with `mutation { registerUser(input: {uuid: "<client uuid>", firstName: "Ana", lastName: "Diaz", email: "ana@example.com"}) { uuid firstName lastName email status } }` returns the new user with that same UUID and `status: ACTIVE`, and the row exists in `user`.
2a. A missing or malformed `uuid` returns `BAD_USER_INPUT` (field `uuid`); reusing a UUID returns `UUID_TAKEN`. Neither inserts anything.
2. Registering the same email again returns an `EMAIL_TAKEN` error and inserts nothing.
3. Missing or invalid fields return `BAD_USER_INPUT` and insert nothing.
4. Adding a new `schema/X.graphql` + `resolver/XRes.js` pair needs no changes to `index.js` files.
5. A request without `query` returns HTTP 400.
6. The server still starts and `/api/health` still works.
7. Submitting the Register screen with valid data creates the user and shows the **Account created** card.
8. Registering an email that already exists shows "Email is already registered." under the Email field.
9. With the server down, the Register screen shows a danger alert instead of failing silently.

## Out of scope — recommendations
| Item | Recommendation |
|---|---|
| Richer client (caching, hooks) | `graphql-request`, or `urql` / `@apollo/client` if you want `useQuery` and caching |
| Password / community on registration | New migration (`password_hash`, `community_id`) and `bcrypt`, in the auth spec |
| Auth (`Auth.graphql`, `AuthRes.js`) and protected resolvers | `jsonwebtoken`; read the token from `context.req` |
| GraphiQL page to try queries in the browser | `ruru`, or serve GraphiQL from a CDN in development only |
| Splitting schemas with type-level resolvers (e.g. `User.company`) | `@graphql-tools/schema` (`makeExecutableSchema`); `buildSchema` + a root object only resolves top-level fields |
| N+1 queries once types reference each other | `dataloader` |
| Rate limiting registration | `express-rate-limit` |
